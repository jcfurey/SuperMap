# Performance and accuracy audit (September 2026)

Scope: the `semantic_mapping` package on `dev` at 8b07e18. Everything below was
measured on this 4-core CPU sandbox (no GPU) with the synthetic scene; no real
capture has been run through the system yet, which is itself the first finding.
This is an assessment: nothing was changed.

## 1. Headline numbers

Pipeline at 640x480, pre-baked detections with masks, 11 objects, 60 frames
(`examples/benchmark.py`):

| stage | mean | p95 | share |
|---|---|---|---|
| appearance embeddings + tracklet prediction (booked as `predict`) | 27 ms | 42 ms | 33% |
| detection back-projection | 14 ms | 16 ms | 17% |
| association (4 stages) | 0.9 ms | 1.1 ms | 1% |
| map update (evidence, fusion, merge, compaction) | 39 ms | 50 ms | 48% |
| scene graph | 0.4 ms | 0.6 ms | 0.5% |
| total per frame | 81 ms | 99 ms | 12 Hz |

The paper's budget is 3 Hz for mapping and 5 Hz for the graph, so the
pipeline has 4x headroom on this machine before the detector. Peak RSS 94 MiB.

Accuracy on the synthetic scene (`examples/evaluate.py`, masks): detection
recall 0.976, change recall 0.959, identity kept across relocation and return
2 / 2, final-map precision 0.80 / recall 1.00 / F1 0.889, mIoU without
background 0.996, mAP50 1.00.

## 2. Performance findings, ranked by impact

### P1. Point-cloud publishing in the node is a Python loop (high)

`SemanticMappingNode._publish_object_points` builds one Python list per point
and hands the list to `point_cloud2.create_cloud`. Measured in the Jazzy image:

| points | list build + create_cloud (today) | structured numpy array |
|---|---|---|
| 13.6 k (the demo map) | 141 ms | 1.8 ms |
| 100 k | 208 ms | 1.1 ms |
| 500 k | 1.4 s | 6.2 ms |

At the default 5 Hz publish rate the demo map alone costs 70% of a core, and a
building-scale map cannot be published at all. `create_cloud` accepts a
structured array directly; the fix is a few lines and removes the problem
entirely. This is the most important item for real hardware.

### P2. Voxel de-duplication uses `np.unique(axis=0)` (high)

Profiling the pipeline: `argsort` inside `np.unique(axis=0)` is 32% of all
pipeline time (1.57 s of 4.97 s over 60 frames). It runs in
`voxel_downsample_indices`, called for every matched instance every frame
(`_fuse_points`) and on merges. Row-wise unique sorts lexicographically over
three int64 columns; packing the three voxel coordinates into one int64 key
gives identical output (verified) and is 9x faster: 19.3 ms vs 2.2 ms per
20 k points. Expected effect: roughly 25-30% off the map-update stage.

### P3. Appearance histograms run on every full-resolution mask pixel (medium)

`ColorHistogramEmbedder` costs 1.0 s over 60 frames (20% of pipeline time):
boolean mask indexing over the whole image plus a 2-D histogram over every
pixel. A 300x300 mask costs 14 ms; subsampling to every 8th pixel gives
4.4 ms with no meaningful change for a 64-bin histogram. Also, this time is
booked under the `predict` stage because the embedding step sits before the
prediction timer; the runtime table therefore overstates tracking and hides
embedding cost. A separate `embed` stage would make the accounting honest.

### P4. Back-projection allocates a full-image mask per box-only detection (low)

`_detection_points_world` creates an image-sized boolean mask for each
detection without a mask, then `back_project_depth` runs `nonzero` over it.
With masks present this is 14 ms per frame at 640x480, dominated by
`nonzero` and the per-detection depth fill crop. Acceptable now; it scales
with detection count and resolution.

### P5. LiDAR rasterization cost at sensor rate (medium, hardware dependent)

`rasterize_depth` on a 200 k point cloud at 640x480 takes 38 ms (an
`argsort` z-buffer). At a 10 Hz sensor rate that is 40% of a core before
anything else, and `pointcloud_accumulate_scans: N` multiplies it. A
bucket-by-pixel minimum (`np.minimum.at` on a flat pixel index) avoids the
sort. The depth fill itself is cheap (8 ms at radius 2 or 3).

### P6. Scaling and memory (good, with a bound to know)

Batched frustum culling keeps the map update at 35 ms with 909 instances
(356 ms exhaustive). Memory is bounded by `max_points_per_object` (20 000
points x 40 bytes = 0.8 MiB per instance worst case), the retired-instance
cap (1000, points released after the grace period), the trajectory cap (200
samples), and the per-cluster edge cache. A 1000-instance live map could
therefore reach 800 MiB of point arrays; 5 000 points per object would be
plenty for the map's purposes and cut that by 4x.

### P7. End-to-end rate is not what the benchmark prints (note)

The 5.3 frames/s "end to end" figure includes the offline detector loading
mask files from disk (38 ms mean, 262 ms max). It says nothing about a real
detector, which runs on the GPU in its own thread at 1 Hz.

## 3. Accuracy findings, ranked by risk

### A1. No real data has been through the system (highest risk)

Every number above comes from a scene with perfect poses, noise-free dense
depth (or synthetic sparsity), axis-aligned box objects, and jittered but
otherwise perfect detections with exact masks. The results are upper bounds.
The parts most exposed on real data, in order:

- Pose drift and depth noise at range feed the geometric-consistency test
  directly. `tau_eps` is 0.15 m; RGB-D depth error beyond 4 m and LiDAR-camera
  extrinsic error of a degree or two both exceed that, which would produce
  false contradictions and false disappearances.
- Detector false positives and label flicker. The tentative stage and the
  Bayesian label fusion exist for this, but their thresholds
  (`min_hits_to_confirm` 2, `min_label_confidence` 0.4, `p_self` 0.85) have
  never been tuned against a real detector.
- Mask quality. Recall drops from 0.98 to 0.69 with boxes only; real masks
  sit between those two.
- Transparent, reflective, and thin objects are missing or wrong in depth
  and would be pruned as contradicted.

The converter, the node's input options, and the evaluation harness are
ready; a single bag with RGB, camera info, depth or a point cloud, odometry,
and TF turns this from a risk into a measurement.

### A2. Final-map precision 0.80 is two removed objects left "occluded" (medium)

The two false positives are the plant and the trash can, which were removed
mid-sequence but whose locations left the field of view before enough
evidence accumulated to confirm the removal. The system reports them as
`occluded`, which is honest, but every consumer (publishers, serialization,
the VLM prompt, the final-map metric) treats occluded as present. Two
improvements are worth considering: an explicit age on occluded instances in
the serialized schema and prompt ("not seen for 27 s"), and an evaluation
convention that scores long-unobserved instances as unknown rather than
present.

### A3. Box geometry: exact on synthetic objects, outlier-sensitive in general (medium)

On the synthetic scene the axis-aligned box centre matches the ground truth
to within 4 mm for every object, while the point mean is off by 0.14-0.46 m
because only visible faces are observed. So the box centre is the right
centroid estimate. Its weakness is the opposite one: a single stray point
inflates the box, and the instance centre and every IoU move with it.
Membership pruning is the guard, and it worked here, but a percentile box
(for example the 2nd to 98th percentile per axis) would be robust by
construction. Extents are consistently +5 cm from the half-voxel padding,
which caps IoU for thin objects (safety sign 0.61, backpack 0.69).

### A4. The 2-D tracker is projection-driven, not motion-driven (low for static scenes)

With `projection_prior_weight` at 1.0 the Kalman prediction of the centre is
replaced outright by the re-projected 3-D box, and the process noise was
inflated so the Mahalanobis gate accepts it. This is the right behaviour for
static objects under ego-motion and it is what makes identities survive
viewpoint change, but it means the filter carries no object motion at all.
Objects that actually move between frames fall back to 3-D re-activation or
re-identification. The paper lists dynamic objects as its own limitation.

### A5. Change-detection thresholds are untuned (medium)

`tau_eps` 0.15 m, `p_hit`/`p_miss` 0.9/0.1, `prune_log_odds` -1.5,
`active_occupied_fraction` 0.6, `disappeared_occupied_fraction` 0.2,
`max_occlusion_frames` 30, `depth_fill_radius_px` 0. They were set by
reasoning and by the synthetic scene. The depth-fill minimum is deliberately
conservative (it can only create occlusion, never free space), but a thin
object narrower than the LiDAR sampling gap can still be judged absent.

### A6. Re-identification limits (medium)

The default descriptor is a chromaticity histogram: it separates the
synthetic objects perfectly and is shading-invariant, but it cannot
distinguish two same-class objects of the same colour. `reid_min_similarity`
0.85 was chosen on the synthetic scene. Reconciliation of a relocated
object's provisional record picks the most similar live instance that
appeared after the retired one was last seen; it has no spatial plausibility
check, so an identical-looking object that appeared elsewhere in that window
could be absorbed. A time window on candidate age, or CLIP descriptors, are
the two mitigations. Box-only detections lose both identities.

### A7. Scene-graph predicates (low)

"On" requires xy IoU above 0.05, so a mug on a large table does not qualify;
"beside" is a 1 m centre distance with overlapping height ranges; clustering
radius is 2 m. There is no "inside" or "near" predicate and no edge weights.
Temporal edges are implicit in the per-instance trajectory (capped at 200
samples), which is what the VLM prompt serializes.

### A8. Evaluation leniency (note)

The true-positive criterion is the paper's (3-D IoU above 0.1, centre within
0.3 m, label match), which is lenient by design. Segmentation label transfer
uses a 0.1 m radius. The "with background" numbers are not comparable to the
paper's Table II because the map never predicts wall, floor, or ceiling.

### A9. Test coverage gap: the node's end-to-end checks are not in the repo (medium)

159 unit tests cover the algorithms, persistence, loaders, and clients, and
CI runs them plus a metric gate. The node itself is exercised only by
scripts that live outside the repository (async detection, VLN query,
save/restore, compressed RGB with depth image, scan accumulation, bag
conversion round trip). They should be checked in and run by the Docker CI
job; until then a node regression would pass CI.

### A10. Timing attribution (note)

`FrameResult.timings["predict"]` includes embedding time (see P3), and the
`total` row excludes the detector. Both are documentation issues, not bugs.

## 4. Recommended order

1. Publish point clouds from structured arrays (P1). Small change, removes
   the one thing that cannot ship on hardware.
2. Hashed voxel keys (P2) and subsampled histograms with a separate `embed`
   stage (P3, A10). Together about 40% off the pipeline cost.
3. Check the node end-to-end scripts into the repo and CI (A9).
4. Run one real bag through converter, evaluation, benchmark, and node (A1),
   then tune the thresholds in A5 and A6 against it.
5. Age on occluded instances in the schema and prompt (A2).
6. Bucketed rasterization for LiDAR (P5), percentile boxes (A3), and a lower
   `max_points_per_object` (P6) as the data indicates.
